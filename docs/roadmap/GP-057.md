# GP-057 --- Admin Team and Role Management

## Status

IMPLEMENTED --- 2026-10-17 ([closure](./GP-057-CLOSURE.md)); admin E2E on local Supabase and production
check pending.

## Objective

A `SUPER_ADMIN` grants, changes and revokes administrative access from `/admin/equipo` instead
of editing `user_roles` by hand, with guardrails that make it impossible to lock the store out
of its own admin.

## Why

ADR-003 defines staff roles and the `staff:manage` permission, but staff provisioning has only
been possible through direct database access.

## Dependencies

GP-022 (Admin Foundation, RBAC guard), ADR-003 (roles, permissions, explicit bootstrap). No
migration: the existing roles and `staff:manage` cover the model.

## Model

| Level in the UI                      | Roles in `user_roles`                                   |
| ------------------------------------ | ------------------------------------------------------- |
| Superadministrador                   | `SUPER_ADMIN`                                           |
| Administrador (acceso operativo)     | `ADMIN_CATALOG` + `ADMIN_ORDERS` + `ADMIN_SUPPORT`      |
| Catálogo / Pedidos y pagos / Soporte | one of `ADMIN_CATALOG`, `ADMIN_ORDERS`, `ADMIN_SUPPORT` |
| Sin acceso (revocar)                 | no staff role (a `CUSTOMER` row, if any, is kept)       |

Granting Superadministrador replaces the operational roles (it already holds every permission).
`inventory:manage`, `ai:manage_credentials`, `audit:export` and `staff:manage` stay exclusive to
`SUPER_ADMIN`, as seeded today.

## Scope

1. Pure planner (`src/lib/admin/staff/levels.ts`): levels, labels, permission summaries, the
   role diff for a change, and the guardrails.
2. Service (`src/lib/admin/staff/service.ts`): team list (staff roles, email from `auth.users`,
   name from `customer_profiles`, last change from the audit log), lookup of a registered
   account by email, and `changeStaffAccess` in one transaction under an advisory lock.
3. Server actions guarded by `staff:manage`; `/admin/equipo` page; "Equipo" nav item.
4. Guardrails, enforced on the server:
   - No change to one's own access (no self-demotion or self-revocation).
   - Never zero `SUPER_ADMIN`: counted inside the locked transaction.
   - Unknown email: the account must register on the store first.
   - Every grant, change and revocation writes an `audit_events` row (`staff:access:grant`,
     `staff:access:change`, `staff:access:revoke`) with previous and new roles.
5. Confirmation dialog for every change, stating the permissions gained or lost.

## Out of Scope

- New roles or permission mappings (a generic `ADMIN` role, `inventory:manage` for operators).
- Inviting accounts that are not registered.
- Listing or searching customers (lookup is by exact email only).

## Acceptance Criteria

- Only `staff:manage` sees the nav item, the page and can run the actions.
- A super admin can grant any level to a registered email, change levels and revoke access.
- Self-changes and removing the last `SUPER_ADMIN` are rejected by the server.
- Each change leaves an audit event with actor, target, previous and new roles.

## Testing / Validation

Unit tests for the planner, actions (permission, validation, error mapping), navigation and the
team workspace; storefront E2E for the unauthenticated redirect; admin E2E (seeded local
Supabase) for the page flow; `pnpm check`, `pnpm test:e2e`.

## Security DoD

Server-side `staff:manage` on page and actions; actor from the verified session only; email
lookup returns only the matched account; advisory lock and in-transaction count for the last
super admin; RBAC is resolved per request, so changes apply on the target's next request.

## Accessibility DoD

Labelled form controls, live status messages, focus-trapped confirmation dialog, Axe clean.

Code, tests, `GP-057-CLOSURE.md`.
