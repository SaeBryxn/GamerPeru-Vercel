# GP-018 --- Checkout

## Status

PLANNED

## Objective

Implement checkout.

## Why

This GP is a roadmap gate that reduces ambiguity for dependent work and
protects the canonical architecture.

## Dependencies

GP-017, GP-004

## Context

Read `AGENTS.md`, the Master Spec, Roadmap, relevant
specs/design/architecture docs, accepted ADRs and prerequisite closure
reports. Later GPs are context only.

## Scope

Identity/contact, Peru shipping address, shipping method selection, payment method selection (Yape/Plin config verification), review, server-authoritative validation, duplicate-safe atomic Order placement, checkout-critical inventory reservation kernel (available_to_sell validation, row locking, InventoryReservation creation, RESERVATION_CREATED ledger entry), initial UNPAID Payment shell creation, initial Shipment record, Cart -> CONVERTED transition, and atomic OrderPlaced OutboxEvent persistence (ADR-009).

## Out of Scope

Payment instruction display, QR rendering, operation-code submission, proof upload, and payment verification (owned by GP-019); broader Order lifecycle transitions, cancellation, and refund services (owned by GP-020); broader Inventory Engine, stock receiving, manual adjustments, multi-location routing, and low-stock signaling (owned by GP-021); outbox background dispatchers and EC OS webhook delivery (owned by GP-042); automatic card payment gateways; promotions/coupons engine.

## Requirements

- Follow canonical specs and accepted ADRs.
- Do not silently expand scope or anticipate later features.
- Document necessary deviations before implementation.
- Preserve multi-brand architecture, Peru-first commerce, Admin
  operability and EC OS independence where relevant.
- Produce validation evidence, not completion claims alone.

## Acceptance Criteria

- Reliable duplicate-safe mobile checkout.
- No unresolved critical contradiction with prerequisites.
- Relevant automated/manual validation is recorded.
- Repository state is clean or intentionally documented.

## Testing / Validation

Execute the smallest sufficient automated and manual validation set.
Include negative/edge cases for stateful, privileged or financial
behavior.

## Functional DoD

All scoped behavior/decision deliverables are complete and acceptance
criteria pass.

agreed budgets.
