# GP-015 --- Authentication

## Status

COMPLETE

## Objective

Implement complete customer and staff authentication infrastructure using **Supabase Auth** with Email/Password and Google OAuth, integrated with Next.js App Router SSR sessions, `getClaims()` cryptographic identity verification, and Gamer Perú server-side RBAC.

## Why

This GP is a roadmap gate that establishes the canonical identity plane, enables secure customer sessions, protects private customer data, and provides the foundation for customer account management (GP-016) and staff authorization.

## Dependencies

GP-003, GP-005, GP-007

## Context

Read `AGENTS.md`, `docs/architecture/TECHNOLOGY_ARCHITECTURE.md`, `docs/architecture/COMMERCE_DOMAIN_MODEL.md`, `docs/decisions/ADR-003-authentication-authorization-rbac.md`, specs, and prerequisite closure reports. Later GPs are context only.

## Scope

1. **Supabase Auth Client/Server Integration (`@supabase/ssr`)**:
   - Configure `@supabase/supabase-js` and pinned `@supabase/ssr` version for Next.js App Router.
   - Implement request-scoped server client factories (`createClient`) avoiding shared module-level state.
   - Implement session cookie management shared between browser and server (`SameSite=Lax`, `Secure` in production, `Path=/`).
   - Implement primary server-side identity verification via `getClaims()`, validating JWT signatures against cached project JWKS.
   - Implement `getUser()` when fresh, authoritative user record validation directly with Supabase Auth servers is required.
   - Conceptual helper `getVerifiedAuthContext()` resolving request-scoped verified claims, `auth_user_id`, and `CustomerProfile` / RBAC mappings.
   - Enforce that `getSession()` user data alone is NEVER accepted as authorization proof in server code.
2. **Canonical Authentication Workflows**:
   - Email/password customer registration, email verification token handling, login, logout, and password recovery/reset.
   - Google OAuth ("Continuar con Google") with PKCE authorization flow, callback route handler, and state verification.
   - Request strictly minimum Google OAuth scopes (`openid`, `email`, `profile`); zero Google provider access/refresh tokens stored in domain tables.
3. **Idempotent Profile Provisioning & Identity Linking**:
   - Implement `ensureCustomerProfile(auth_user_id)` to initialize `CustomerProfile` on first authenticated login (supporting both email/password signup and Google OAuth first login).
   - Ensure concurrency safety under unique constraint on non-null `auth_user_id`.
   - Handle same-email identity linking natively through Supabase Auth.
4. **Email Pipeline Separation**:
   - Verify Resend custom SMTP configuration in Supabase Auth project settings for all authentication emails (signup confirmation, verification, password recovery/reset).
   - Ensure password resets are handled exclusively by the Supabase Auth SMTP pipeline, never dispatched via Gamer Perú Inngest.
5. **Caching & Security Boundaries**:
   - Enforce dynamic (`no-store`) rendering on authenticated routes; ensure responses setting or refreshing session cookies are not publicly cached or statically generated with ISR.
   - Enforce decoupling between Supabase identity (`auth.users`) and Gamer Perú RBAC (`UserRole`, `RolePermission`).
   - Rate limiting, abuse mitigation, and password recovery security review.

## Out of Scope

- Customer account portal UI features beyond authentication (saved addresses, order history, wishlist in GP-016).
- Admin operational portal features beyond authentication/RBAC boundary verification.

## Requirements

- Follow canonical specs and accepted ADRs (especially amended ADR-003).
- Do NOT implement custom credential hashing (Argon2id) or custom database session tables; delegate credential verification to Supabase Auth.
- Do NOT store or duplicate password hashes in Gamer Perú domain tables.
- Do NOT place authoritative RBAC roles in user-editable metadata.
- Preserve multi-brand architecture, Peru-first commerce, Admin operability, and EC OS independence.
- Produce validation evidence, not completion claims alone.

## Acceptance Criteria

- Functional email/password registration, verification, login, logout, and recovery flows.
- Functional Google OAuth authentication flow with Next.js SSR session cookies.
- Idempotent `CustomerProfile` creation linked to `auth_user_id` (`UUID`).
- Verified server-side session helper (`getClaims()`) rejects forged or unverified tokens.
- Authenticated responses are never publicly cached or statically pre-rendered with session cookies.
- No unresolved critical contradiction with prerequisites.
- Automated tests covering auth helpers, server actions, and profile provisioning.

## Testing / Validation

Execute automated and manual validation sets covering:

1. **Email/Password Signup & Verification**: Valid and invalid payloads, email verification token handling.
2. **Password Recovery Flow**: Recovery request, signed reset token verification, and password update.
3. **Google OAuth Callback**: PKCE authorization flow, state validation, and session creation.
4. **Token Signature Verification**: Tampered cookie / JWT payload rejected by `getClaims()`.
5. **Session Expiry & Refresh**: Expired access token rotated correctly using valid refresh token; invalid refresh token handled gracefully.
6. **Cache Boundary**: Authenticated routes confirmed dynamic; no `Set-Cookie` headers cached publicly.
7. **Identity Linking**: Multiple auth methods sharing the same verified email resolve to the same `auth.users` record and single `CustomerProfile`.
8. **Concurrency**: Concurrent `ensureCustomerProfile(auth_user_id)` calls safely resolve to exactly one profile record.
9. **RBAC Isolation**: Google OAuth login never grants staff/admin roles.
10. **Identity Detachment**: Deleted/detached identity (`auth_user_id = NULL`) cannot access historical account data.
