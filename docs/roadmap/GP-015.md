# GP-015 --- Authentication

## Status

PLANNED

## Objective

Implement complete customer and staff authentication infrastructure using **Supabase Auth** with Email/Password and Google OAuth, integrated with Next.js App Router SSR sessions and Gamer Perú server-side RBAC.

## Why

This GP is a roadmap gate that establishes the canonical identity plane, enables secure customer sessions, protects private customer data, and provides the foundation for customer account management (GP-016) and staff authorization.

## Dependencies

GP-003, GP-005, GP-007

## Context

Read `AGENTS.md`, `docs/architecture/TECHNOLOGY_ARCHITECTURE.md`, `docs/architecture/COMMERCE_DOMAIN_MODEL.md`, `docs/decisions/ADR-003-authentication-authorization-rbac.md`, specs, and prerequisite closure reports. Later GPs are context only.

## Scope

1. **Supabase Auth Client/Server Integration**:
   - Configure `@supabase/supabase-js` and `@supabase/ssr` for Next.js App Router.
   - Implement secure HTTP-only cookie session handling with PKCE authorization flow for OAuth.
   - Implement verified server-side identity helper (`getUser()`), preventing reliance on unverified client session data.
2. **Canonical Authentication Workflows**:
   - Email/password customer registration, email verification token handling, login, logout, and password recovery/reset.
   - Google OAuth ("Continuar con Google") login flow, callback route handler, and state verification.
3. **Idempotent Profile Provisioning**:
   - Implement `ensureCustomerProfile(auth_user_id)` to initialize `CustomerProfile` on first authenticated login (supporting both email/password signup and Google OAuth first login).
4. **Email Integration**:
   - Document and verify Resend custom SMTP configuration for Supabase Auth transactional emails.
5. **Security & Abuse Protection**:
   - Rate limiting, authentication abuse mitigation, and password recovery security review.
   - Enforce decoupling between Supabase identity (`auth.users`) and Gamer Perú RBAC (`UserRole`, `RolePermission`).

## Out of Scope

- Customer account portal UI features beyond authentication (saved addresses, order history, wishlist in GP-016).
- Admin operational portal features beyond authentication/RBAC boundary verification.

## Requirements

- Follow canonical specs and accepted ADRs (especially amended ADR-003).
- Do NOT implement custom credential hashing (Argon2id) or custom database session tables; delegate credential verification to Supabase Auth.
- Do NOT store or duplicate password hashes in Gamer Perú domain tables.
- Do NOT place authoritative RBAC roles in user-editable metadata.
- Preserve multi-brand architecture, Peru-first commerce, Admin operability, and EC OS independence.
- Produce validation evidence, not completion claims alone.

## Acceptance Criteria

- Functional email/password registration, verification, login, logout, and recovery flows.
- Functional Google OAuth authentication flow with Next.js SSR session cookies.
- Idempotent `CustomerProfile` creation linked to `auth_user_id` (`UUID`).
- Verified server-side session helper rejects forged or unverified tokens.
- No unresolved critical contradiction with prerequisites.
- Automated tests covering auth helpers, server actions, and profile provisioning.

## Testing / Validation

Execute automated and manual validation sets covering:
- Email/password signup with valid/invalid payloads.
- Password recovery request and token verification.
- Google OAuth callback flow and session creation.
- Server-side `getUser()` validation vs tampered cookie payloads.
- Idempotent `CustomerProfile` creation ensuring duplicate accounts are not created for the same `auth_user_id`.

## Functional DoD

All scoped authentication workflows, SSR cookie handlers, profile provisioning, and acceptance criteria pass.

## Visual DoD

Preserve Gamer Perú design language across login/signup/recovery dialogs and pages.

## Performance DoD

No unjustified performance regression in SSR session resolution.

## SEO DoD

Preserve established SEO architecture; public routes require zero authentication overhead.

## Security DoD

Required: validate server-side authorization, input/data handling, abuse mitigation, short-lived JWT validation, and sensitive-operation implications.

## Accessibility DoD

User-facing authentication UI must handle keyboard navigation, visible focus indicators, accessible error announcements, and reduced motion.
